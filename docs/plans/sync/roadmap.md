# 동기화 통합 — 로드맵

_작성일: 2026-11-01_
_상태: 계획 (작가 검토 대기)_
_관련: linetta-artworks `docs/plans/artworks-phase-11-private-vault.md`(비공개 보관함), `linetta#267`~`#283`_

## Overview

지금 앱에는 비슷한 이름의 기능이 흩어져 있다.

- 갤러리의 "보관함"은 작품을 목록에서 치워 두는 archive다.
- "동기화"(GitHub, 폴더)는 Markdown을 내보내기만 하고, 하루에 한 번 돈다. 앱으로 되돌아오지 않는다.
- "비공개 보관함"은 작품을 암호화해 Linetta Works로 옮기지만 수동이고, 작품별로 하나씩이다.

이번 작업으로 **동기화를 하나로 합친다.** 대상은 Linetta Works, GitHub, 폴더 세 가지이고, 옮기는 항목은 같으며, 자동으로 돈다.

## 가치 제안

> 작가는 어느 기기에서든 동기화를 연결하면 같은 작품을 같은 상태로 이어 쓴다.
> 무엇을 옮길지는 한 번 고르고, 그 뒤로는 동기화를 의식하지 않는다.

## 완료 조건

- 기기 A에서 고친 작품이 기기 B를 켜 두기만 해도 몇 분 안에 들어온다
- 새 기기에서 연결과 복구 키 입력만 하면 전체 작품, 전역 스킬, 작가 프로필이 들어온다
- 고른 항목만 옮겨지고, 끈 항목은 어느 기기에서도 지워지지 않는다
- 두 기기에서 같은 작품을 고치면 양쪽 원고가 남고, 작가가 고른다
- 자동 동기화가 멈추면 작가가 알 수 있다. 조용히 실패하지 않는다

## 실측 (2026-11-01, 작가의 서재, 작품 6편)

| 항목 | 크기 | 비중 |
|---|---|---|
| 삽화 29장 | 9.5 MB | 약 67% |
| 참조 이미지 | 1.5 MB | 약 10% |
| 버전 이력(`node_snapshots`) | 약 3 MB | 약 21% |
| 원고 본문(`content_doc`) | 0.26 MB | 약 2% |
| 작가 프로필 | 440바이트 | |
| 전역 스킬 5개 | 20 KB 미만 | |

전체가 약 14 MB로, 기본 쿼터 200 MiB의 7% 정도다. 삽화를 끄는 선택은 쿼터 때문이 아니라 Git 저장소 크기와 데이터 사용량 때문에 의미가 있다.

## 결정 사항

1. **용어를 정리한다.** 갤러리 보관함은 한글 "아카이브", 영어 "Archive", 일본어 "アーカイブ"다. 비공개 보관함은 "Linetta Works 동기화"가 된다. 코드, RPC, DB, URL의 `vault`는 그대로 둔다. 이름 때문에 마이그레이션과 호환성을 건드릴 이유가 없다.
2. **세 대상은 같은 스냅샷 형식을 쓴다.** 항목 선택, 암호화, 충돌 판정, 복원 지점이 코드 한 벌이다. GitHub와 폴더는 `.linetta/` 아래에 봉인된 조각을 두는 저장소가 된다.
3. **GitHub와 폴더의 복원 데이터도 암호화한다.** 공개 저장소일 수 있고, 전역 스킬과 작가 프로필까지 실린다. 사람이 읽는 Markdown 내보내기는 지금처럼 함께 쓴다. 복구 키를 잃어도 Markdown은 남는다.
4. **양방향은 기본 대상 하나만이다.** 작가가 기본 동기화를 하나 고른다. 나머지 대상은 올리기만 하는 미러이고, 필요할 때 수동으로 복원한다. 세 곳이 모두 양방향이면 충돌 조합이 늘고, 어느 쪽이 진짜인지 알 수 없게 된다.
5. **항목 선택은 계정 단위다.** 기기마다 다르면 삽화를 끈 기기가 올린 리비전이 켠 기기의 최신본을 밀어내, 어떤 기기에서는 삽화가 영영 들어오지 않는다. 선택은 서재 항목(결정 7)에 봉인해 모든 기기가 따른다.
6. **끈 항목은 받을 때 건드리지 않는다.** 매니페스트에 빠진 범주를 적고, `Apply`는 그 범주의 표와 파일을 지우지도 쓰지도 않는다.
7. **전역 스킬과 작가 프로필은 작품 밖의 "서재 항목"으로 옮긴다.** 복구 키에서 유도한 고정 ID의 항목 하나다. 서버는 보통 항목으로 보므로 서버 변경이 없다. 충돌은 묻지 않고 새 것이 이기며, 진 쪽은 스킬 이력과 복원 지점에 남는다.
8. **에이전트 대화와 사용 내역, 프로바이더 설정은 옮기지 않는다.** `ai_runs`, `companion_*`, `mcp_activity`, API 키는 제외를 유지한다.
9. **자동 동기화는 작품 단위 스냅샷을 유지한다.** 행 단위 병합이나 실시간 공동 편집은 하지 않는다. 한 번에 한 기기에서 쓰는 사용을 전제로 한다. 오프라인에서 양쪽을 고치면 충돌 화면이 나온다.
10. **자동으로 받는 것은 로컬이 변하지 않은 작품뿐이다.** 그 경우 로컬은 서버의 기준 리비전과 같으므로 잃을 것이 없다. 충돌은 자동으로 처리하지 않는다.
11. **아카이브한 작품도 동기화한다.** 아카이브 상태 자체가 기기 간에 공유돼야 한다. 지금 GitHub와 폴더가 아카이브를 건너뛰는 것은 Markdown 내보내기에만 남긴다.
12. **삭제는 전파하되 다른 기기에서는 아카이브로 옮긴다.** 한 기기의 실수나 버그가 모든 기기의 원고를 지우지 않게 한다. 진짜 삭제는 그 기기에서 작가가 직접 한다.
13. **약관은 한 번만 올린다.** 다른 작가를 허가하기 전에 이름, 전역 항목, 자동 전송을 함께 반영해 `TERMS_VERSION`을 2로 올린다. 지금 재동의할 사람은 운영자 한 명이다.
14. **운영자 허가제는 그대로다.** Linetta Works 대상만 허가가 필요하고, GitHub와 폴더는 필요 없다. 복구 키는 대상과 관계없이 서재에 하나다.

## Out of Scope

- 에이전트 대화·사용 내역 동기화 (결정 8)
- iOS·Android 앱의 동기화. `vault`는 지금 `!mobile` 빌드에만 있다
- 행 단위 병합, 실시간 공동 편집
- 작품별 항목 선택과 작품별 동기화 제외. 먼저 계정 단위로 쓰고 판단한다
- 유료 요금제, 쿼터 변경

## 확인되지 않은 가정

- **`Export`를 주기적으로 돌려도 가볍다.** 전체 표와 그림을 읽어 해시를 낸다. Phase 3 첫 작업에서 큰 작품으로 재고, 느리면 `PRAGMA data_version`으로 거른다.
- **자동 올리기의 전송량이 감당할 만하다.** `tables/node_snapshots` 파트는 작품의 전체 스냅샷이라, 씬 하나만 고쳐도 통째로 다시 올라간다. 지금 큰 작품 기준 1 MB 안팎으로 본다. 많으면 파트를 씬별로 나누는 형식 변경을 Phase 3 안에서 검토한다.
- **GitHub 저장소 크기가 감당할 만하다.** 봉인된 조각은 압축되지 않고, Git 이력에서 사라지지 않는다. 미러는 하루 한 번을 유지한다. 기본 대상으로 쓰면 경고를 띄운다.
- **앱이 열린 작품, 편집 시각, 에이전트 실행 상태를 엔진에 알릴 수 있다.** Phase 3에서 확인한다.

## 비공개 보관함 Phase 11과의 관계

- Phase 11의 서버, 암호화, 번들, 충돌 처리는 그대로 쓴다.
- 자동 검증은 2026-11-01에 통과했다. 수동 Checkpoint 중 앱 화면 항목은 Phase 3 Checkpoint에서 자동 동작까지 포함해 함께 본다. 그래서 "Phase 11 완료" 승인은 Phase 3 뒤로 미룬다.
- `linetta#283`의 게시 안내가 든 앱 릴리스 전에는 다른 작가를 허가하지 않는다는 조건을 "약관 v2와 Phase 3이 든 앱 릴리스 전"으로 바꾼다.
