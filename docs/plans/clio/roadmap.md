_작성일: 2026-11-04_

## Overview

SNS 글(X, Threads)과 짧은 일반 글을 쓸 때 쓰는 **작성자 주도** 글쓰기 도구다. 글은 내가 쓴다. 앱은 내 과거 글로 잰 말투를 기준으로, 내 글에서 벗어난 곳과 AI 티가 나는 곳을 짚는다. 고칠 때는 내가 원하는 곳만 내 말투로 제안한다.

리네타와 **같은 저장소의 별도 데스크톱 앱**이다. Go 엔진 패키지(`style`, `provider`, `settings`, `store`, `rpc`)를 함께 쓴다. 리네타의 작품 → 챕터 → 씬 구조는 짧은 글 단위와 맞지 않는다. 반면 `engine/internal/*`은 같은 Go 모듈 안에서만 import할 수 있다. 그래서 앱은 나누고 저장소는 하나로 둔다.

먼저 본인용으로 만든다. 대상은 devlikebear의 X 글이다. 2주 동안 실제로 써 본 뒤 배포를 별도 로드맵으로 정한다.

## 가치 제안

> 나는 내 말투로 쓰고, 앱은 내 글이 나답지 않거나 AI 같아지는 순간을 짚는다.
> 대신 써 주는 대필 도구가 아니라, 내 과거 글을 기준으로 삼는 교정자다.

## 근거 (실측, 2026-11-04)

run-12의 조건: 내 X 글 150편(게시물 112, 답글 38) 중 학습 138편, 시험 12편, 모델은 Sonnet 5.5. A는 메모만 준 글, B는 말투 프로필과 비슷한 글을 함께 준 글, C는 B를 측정값에 맞춰 한 번 고친 글이다.

| 지표 | 원문 | A | B | C |
|---|---|---|---|---|
| 평균 \|z\| (학습 글과의 거리) | 0.26 | 0.31 | 0.25 | 0.19 |
| 이모지 / 느낌표 (글당) | 0.08 / 0 | 0.42 / 0.17 | 0 / 0 | 0 / 0 |
| 존댓말 비율 | 0.39 | 0.30 | 0.01 | 0.07 |
| 줄 수 | 2.92 | 2.67 | 2.33 | 1.33 |
| 자주 쓰는 끝맺음 8개 비중 | 31% | 34% | 49% | 67% |

이 표에서 읽은 것:

1. **프로필과 비슷한 글(B)은 AI 티를 지운다.** 이모지와 느낌표가 사라지고, 학습 글과의 거리가 원문의 흔들림 수준(0.25 대 0.26)까지 온다.
2. **측정값에 맞춘 고쳐 쓰기(C)는 글을 평균으로 깎는다.** 끝맺음이 몇 개로 몰리고 줄바꿈이 사라진다. 거리 0.19는 사람 글의 흔들림보다도 낮다.
3. **말투 전환을 놓친다.** 답글과 공지는 존댓말, 혼잣말은 반말이다. B와 C는 이것을 반말 하나로 뭉갠다.
4. 시험 글이 12편이라 0.05 차이는 잡음이다. 블라인드 평가(`blind.html`)는 아직 하지 않았다.
5. **표면 규칙만으로는 매끈한 AI 글을 못 잡는다.** 사전 계산에서 이모지·느낌표·AI 표현으로 짚히는 A는 12편 중 4편이었다. 반대로 "X 글에서 존댓말이면 지적"은 원문 3편을 잘못 짚는다. 작가는 X 글 공지에 존댓말을 쓴다(9편, 8%). 그래서 검사기는 "작가가 한 번도 안 하는 것"만 짚고, 나머지는 Phase 2에서 작가가 직접 짚은 특징으로 규칙을 하나씩 늘린다.

맥락별 존댓말 비율(`x-posts.json`): X 글 0.08, X 답글 0.33.

경쟁 리서치(2026-11-04): 말투 학습을 내세우는 생성기는 10개가 넘는다(Typefully, Spiral Style Engine 등). 대부분 영어 중심이고, 클라우드 구독이며, 대필 구조다. 빈자리는 세 가지가 겹치는 곳이다. **한국어 말투**, **작성자 주도**, **로컬 저장**.

## 결정 사항

1. **별도 앱, 같은 저장소.** 앱은 `apps/clio`, 엔진 진입점은 `engine/cmd/clio-ffi`, 엔진 코드는 `engine/internal/clio/*`에 둔다. 6월에 만든 빈 리포 `~/workspace/myworks/clio`의 계획(블로그·일기·소셜 통합)은 이 문서로 대체한다.
2. **검사기가 먼저, 생성은 나중.** Phase 2가 끝나면 모델 호출 없이도 쓸 수 있어야 한다. 검사는 결정론적이고 무료이며, 실험에서 차이가 가장 분명했던 축이다.
3. **말투는 맥락별로 잰다.** 맥락은 플랫폼(`x`, `threads`, `blog`) × 종류(`post`, `reply`)다. 내 스레드에 내가 단 답글(내 글의 연속)은 `post`로 센다. 표본이 20편 미만인 맥락은 같은 플랫폼 전체로, 그것도 모자라면 전체 글로 물러난다.
4. **자동 고쳐 쓰기 루프는 없다.** C처럼 측정값에 맞춰 통째로 다시 쓰지 않는다. 짚은 곳마다 제안을 받고, 작가가 하나씩 받거나 버린다.
5. **기준은 내 글 대비 상대값이다.** 절대 금지어 대신 "내 글 10~90 백분위 밖", "내 글에 한 번도 없는 AI 표현"처럼 판단한다. 작가가 원래 쓰는 표현은 짚지 않는다.
6. **데이터는 리네타와 분리한다.** 홈은 `com.devlikebear.clio`, DB는 `<home>/clio.db`, 마이그레이션 체인과 키체인 서비스(`devlikebear.clio`)도 따로 둔다. 리네타의 `library.db`는 건드리지 않는다.
7. **게시는 딥링크와 복사로만 한다.** API나 OAuth는 쓰지 않는다. 리네타 `apps/desktop/src/lib/share.ts`의 intent URL 방식을 따른다.
8. **한국어 UI만 둔다.** i18n 구조는 리네타처럼 두되 `ko` 카탈로그만 채운다.

## 기술 스택 / 환경

- **엔진**: Go 1.26, 모듈 `github.com/devlikebear/linetta/engine`, modernc SQLite(단일 연결), tars `pkg/llm`(`internal/provider`를 통해서만 사용)
- **앱 셸**: Tauri 2.12, 크레이트 `clio-desktop`, identifier `com.devlikebear.clio`, 개발 포트 1430(리네타는 1420)
- **프런트엔드**: React 18, TypeScript, Vite 5, `react-router-dom` 7, vitest, pnpm 11. `apps/clio`는 독립 pnpm 프로젝트로 두고 워크스페이스는 만들지 않는다(리네타와 같은 방식)
- **브리지**: Go c-archive → Rust FFI. `apps/desktop/src-tauri/src/ffi.rs`와 `engine/cmd/linetta-ffi/ffi.go`를 이름만 바꿔 복사한다
- **빌드 대상**: macOS(로컬)와 Linux(CI 검사만). Windows, iOS, 스토어 빌드는 하지 않는다
- **로컬 검증**: `engine/`에서 `CGO_ENABLED=0 go test ./...`. cgo 빌드는 macOS 키체인을 건드려 멈출 수 있다

## 공통 컨벤션 (리네타와 같음)

| 항목 | 규칙 | 참조 |
|---|---|---|
| RPC 핸들러 | `func X(deps...) rpc.Handler` 팩토리, 타입 있는 params 구조체, 패키지별 에러 → reason 맵 | `engine/internal/rpc/handlers/style.go` |
| RPC 에러 | `*rpc.MethodError`, `rpc.NotFound(reason, msg)`, 내용 충돌은 `CodeContentConflict` | `engine/internal/rpc/reason.go` |
| 마이그레이션 | `NNNN_name.sql`. 적용된 파일은 체크섬이 기록되므로 고치지 않는다 | `engine/internal/store/migrations/` |
| SQLite | 연결 하나. `Rows`를 연 채로 다시 쿼리하지 않는다(교착) | `engine/internal/store/store.go` |
| LLM 의존 | `tars/pkg/llm`은 `provider`와 `agent`만 import한다. Clio 패키지는 `Ask(ctx, prompt)` 인터페이스로 받는다 | `scripts/validate-story-core-deps.sh` |
| 렌더러 허용 메서드 | 새 RPC는 Clio의 `RENDERER_ENGINE_METHODS`에 정렬해서 넣는다(테스트가 순서를 검사) | `apps/desktop/src-tauri/src/lib.rs` |
| 외부 URL | https만, 호스트 허용 목록(`x.com`, `www.threads.com`) | `open_external_url` |
| 디자인 토큰 | `App.css`의 CSS 변수. Clio는 `--c-` 접두사 | `apps/desktop/src/App.css` |
| 작가 글 | 실제 게시물은 저장소에 넣지 않는다. 테스트는 합성 글로, 실측은 저장소 밖 경로로 | PR #319 |

## Out of Scope

- 스토어 배포, 서명, 자동 업데이트, Windows/Linux 패키징: 본인용으로 먼저 판단한다
- 영어/일본어 UI, 온보딩: 같은 이유
- X/Threads API 직접 게시, 예약 게시, 반응 분석: 딥링크로 충분하고, OAuth 유지 비용이 크다
- Instagram 이미지와 캡션 편집: 글이 아니라 이미지 중심이라 다른 문제다
- 로컬 모델 파인튜닝(LoRA, DPO): 프롬프트와 검사로 먼저 한계를 본다
- 리네타와의 데이터 동기화, 모바일 앱
- 형태소 분석기: 끝맺음은 실험과 같은 "마지막 한글 2글자"로 시작한다
- 블로그 같은 긴 글 전용 기능(제목, 태그, 마크다운): `blog` 맥락은 받되 편집기는 짧은 글 기준이다

## 페이즈 구성

각 페이즈는 끝나면 앱에서 직접 써 볼 수 있는 수직 슬라이스다.

### Phase 1: 뼈대와 내 말투 — 앱이 뜨고, 내 글을 넣으면 맥락별 프로필이 보인다

- **목표**: `make clio-dev`로 Clio 창이 뜬다. `x-posts.json`을 가져오면 맥락별 수치와 자주 쓰는 끝맺음이 보인다
- **포함 기능**: 엔진 공용부(홈, 마이그레이션 체인, 키체인 서비스) 주입, 글 가져오기, 말투 프로필, 앱 셸
- **예상 소요**: 3일
- **작업지시서**: [`phase-1-shell-and-voice.md`](./phase-1-shell-and-voice.md)
- **Checkpoint 요약**: Go가 계산한 전체 프로필이 `eval-voice.py`와 같은 글 묶음에서 0.01 안으로 맞는다

### Phase 2: 검사기 — 쓰는 동안 짚는다 (모델 호출 없음)

- **목표**: 초안을 쓰면 AI 표현, 말투 불일치, 범위 이탈이 줄 단위로 표시된다
- **포함 기능**: 검사 규칙 4종, 초안 저장, 편집기와 하이라이트, X 글자 수, run-12 기준치 측정
- **예상 소요**: 3일
- **작업지시서**: [`phase-2-checker.md`](./phase-2-checker.md)
- **Checkpoint 요약**: run-12에서 원문은 12편 중 1편 이하, A는 4편 이상 짚힌다

### Phase 3: 제안 — 짚은 곳만 내 말투로 고친다

- **목표**: 짚은 곳을 누르면 내 말투 후보 1~3개가 나오고, 받으면 버전이 남는다
- **포함 기능**: 프로바이더 설정, 구간 제안, 메모로 초안 쓰기(B 방식), 버전과 되돌리기
- **예상 소요**: 3일
- **작업지시서**: [`phase-3-suggest.md`](./phase-3-suggest.md)
- **Checkpoint 요약**: 제안을 받은 결과에 새 강한 지적이 생기지 않고, 맥락의 존댓말/반말을 지킨다

### Phase 4: 내보내기와 되먹임 — 게시하고, 게시한 글이 다시 기준이 된다

- **목표**: X와 Threads로 넘기고, 게시한 글이 프로필에 들어가고, 2주 사용 기록이 쌓인다
- **포함 기능**: 복사와 intent 링크, 게시 표시, 프로필 갱신, 사용 통계, CI 작업
- **예상 소요**: 2일
- **작업지시서**: [`phase-4-publish-and-loop.md`](./phase-4-publish-and-loop.md)
- **Checkpoint 요약**: 게시로 표시한 초안이 글 목록과 프로필의 글 수에 반영된다

## 페이즈 간 의존성

```
Phase 1 (뼈대, 프로필)
  └─→ Phase 2 (검사기)
        ├─→ Phase 3 (제안)        ← 게이트: blind.html 평가 기록
        └─→ Phase 4 (내보내기, 되먹임)
```

**병렬 가능성**: Phase 4는 Phase 2만 있으면 된다. Phase 3과 순서를 바꿔도 된다.

**Phase 3 게이트**: Phase 3을 시작하기 전에 run-12의 `blind.html`을 직접 매기고 결과를 `eval-check.md`에 적는다. B를 원문으로 고른 횟수가 12묶음 중 3회(무작위 수준) 이상이거나, B의 '나 같음' 평균이 원문보다 0.5점 넘게 낮지 않으면 계획대로 간다. 둘 다 아니면 Phase 3은 "구간 후보 제안"만 남기고, "메모로 초안 쓰기"는 뺀다.

## 페이즈 간 전환 규칙

1. 작업지시서의 모든 체크박스를 끝낸다
2. Checkpoint 블록의 검증을 모두 통과한다
3. 작가가 "Phase N 완료 확인, 다음 진행"이라고 명시적으로 승인한다
